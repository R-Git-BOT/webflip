# ADR 0001: MVPの実行時アーキテクチャ

- Status: Superseded by ADR 0005
- Date: 2026-10-02

## Context

MVPは同時20ルーム、同時参加者合計100人を扱い、将来はアプリケーションサーバーを複数台へ増やせる必要がある。一方、MVPで複数台構成を運用する複雑さは避けたい。

ルームでは、確定、退出、除外、タイマー終了などが同時に発生し得る。ブラウザごとに状態遷移を決めると、一斉提出の重複や参加資格の不一致が起こる。また、サーバー再起動後に進行中ルームを復元しないという製品仕様を維持する必要がある。

## Decision

- MVPは、1台のLinuxサーバー上で1つのアプリケーションインスタンスと共有一時ストアをコンテナとして稼働させる。
- 進行規則を深い `RoomEngine` Moduleに集約する。そのInterfaceは、ルームへ加えるコマンドと、返却する結果・イベントを中心とした小さなものにする。
- HTTP、WebSocket、共有一時ストアを `RoomEngine` の外側に置くAdapterとする。
- 保存Interfaceには、運用時の共有一時ストアAdapterとテスト時のメモリAdapterを接続できるSeamを設ける。
- リアルタイムの状態通知にはWebSocketを使用し、ページ取得、認証、ルーム作成などにはHTTPを使用する。
- サーバーをルーム状態と期限の唯一の正とし、同時に届いたコマンドを順序付けて状態遷移を一度だけ実行する。
- 各アプリケーション起動に世代識別子を持たせる。以前の世代が作成したルームは復元せず、終了扱いにする。
- 共有一時ストア上のルームデータはアプリケーションから定期更新される有効期限を持ち、更新停止後10分以内に削除する。

## Consequences

- MVPの運用構成は1台のままでも、ルーム状態がプロセス内メモリへ閉じないため、将来の複数インスタンス化に必要な変更を局所化できる。
- `RoomEngine` のInterfaceが主要なテスト面になり、HTTPやWebSocketを起動せず進行規則を検証できる。
- ブラウザはサーバーの結果を表示する役割となり、競合時の最終判断を持たない。
- 共有一時ストアとその監視・バックアップ不要設定を運用する負担が増える。
- 一時ストアにデータが残っていても、アプリケーション再起動後のルームは復元されない。
- 将来複数インスタンス化する際は、WebSocketイベントをインスタンス間で中継するAdapterの追加が必要になる。
